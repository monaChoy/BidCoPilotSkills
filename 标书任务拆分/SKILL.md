# 标书任务拆分

产出 `投标输出/<项目名>/写作任务清单.md`。任务以可独立交付的章节文件为基本粒度，声明真实依赖和完成条件；不修改已冻结spec，不建立外部议题或投标管理台账。

## 1. 确认拆分依据

- 读取项目 `AGENTS.md`，定位完整招标文件、有效澄清、已冻结的 `标书目录.md`、`标书初稿讨论.md`、用户要求的拆分范围和输出目录。
- 核对spec已经用户确认冻结，且对应当前招标文件、澄清和目录；不存在、未冻结或已经失效时，先使用 `标书spec`。
- 若已有 `写作任务清单.md`，读取其编号和状态；更新拆分时保留未改变任务的稳定编号与状态，新任务使用下一个未用编号，不重排旧编号，不覆盖已完成结果。

完成标准：项目输入完整，spec当前有效，全量或指定部分的拆分范围已确认，已有任务状态已摄入。

## 2. 草拟写作任务

按冻结目录和spec计划落点拆分：

- 默认一个任务交付一个章节Markdown文件，使招标要求、spec决策、事实素材和正文响应形成一条可验收路径。
- 方案章节仅在冻结目录已有可独立叶子章节时继续拆分；不把每个小标题机械变成任务，不创建正文碎片。
- 一个评分点涉及多个章节时，按已冻结的主落点和相关落点分别归入对应任务；不为评分点重复创建同名正文。
- 按依赖顺序编号 `W-001`、`W-002`。只有前一任务的正文结果确实是后一任务的必要输入时才建立阻塞关系；共同读取项目档案、招标文件或spec不构成任务间依赖。
- 缺少投标人事实时允许任务继续，并要求正文使用【待补】且登记到README；缺少会改变内容边界或写法的写作决策时，将相关任务标为“阻塞”。
- 若发现计划落点遗漏、重叠或无法独立交付，停止相关任务的拆分，向用户报告具体spec缺陷并使用 `标书spec` 追加决策；不得直接修改冻结结论。

每项任务使用以下最小结构：

```markdown
### W-001 <任务标题>
- 范围：<对应目录章节或评分点>
- spec依据：<决策编号和计划落点>
- 招标依据：<文件/页码/条款>
- 依赖：<任务编号；无则写“无”>
- 输出：<章节Markdown文件>
- 完成条件：<可核对的正文响应、证据或待补登记>
- 状态：未开始 / 进行中 / 阻塞 / 已完成
```

完成标准：本次拆分范围内每个计划落点只有一个主任务；每个任务可独立验收；依赖均为真实阻塞关系。

## 3. 确认粒度与依赖

按编号向用户通读任务标题、依赖和交付内容，集中询问：

1. 粒度是否过粗或过细；
2. 阻塞关系是否真实；
3. 是否需要合并、继续拆分或排除任务。

用户确认前不写入或替换任务清单。用户只要求一次性撰写指定部分时，停止拆分并提示直接使用 `标书撰写`。

完成标准：用户明确确认任务边界和依赖。

## 4. 写入任务清单并交棒

写入单一文件：

```markdown
# <项目名> 写作任务清单

## 共同输入
- 项目档案：<路径>
- 招标文件及有效澄清：<路径>
- 标书目录：<路径>
- 标书spec：<路径>

## 写作任务
<已确认任务>
```

新任务初始状态为“未开始”。提示用户使用 `标书撰写`，可指定任务编号、章节、目录范围或评分点；匹配不唯一时由撰写技能列出候选并确认。任务清单只负责拆分和交接，不撰写正文，也不因部分任务完成而触发完整标书检查。

完成标准：任务清单与冻结目录和spec一致，编号稳定，状态和依赖可追踪。
