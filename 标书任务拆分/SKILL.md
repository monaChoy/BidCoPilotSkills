# 标书任务拆分

产出 `投标输出/<项目名>/写作任务清单.md`。不在技能之外另建议题跟踪或管理台账。

## 1. 核对依据

读取项目 `AGENTS.md`、当前招标及澄清、目录、spec 和已有任务清单。缺项目档案的先建档；缺可执行设计的，用 `标书spec` 补齐本次范围的设计。

只有依据已确认、且不受待核事项影响的章节，才排为可执行任务；其余写明阻塞原因，不要因为局部问题让无关章节一起等整个 spec 冻结。核对来源版本和当前有效决策，不执行已被替代的旧结论。

## 2. 拆分

- 默认一个任务交付一个可独立验收的章节文件；不要把每个清单行、小标题或评分点机械地拆成任务。
- 每个计划响应位置只设一个主任务，其他任务引用它的结果；只有确实需要前一任务的正文才能完成时，才设置任务依赖，共读同一份招标文件不构成依赖。
- 缺事实材料的可以用【待补】继续；缺内容边界决定的，阻塞相关任务。
- 已有清单保留稳定编号和有效状态。需求变更导致已完成任务失效时，保留旧成果，把任务标为"需更新"并写明原因，不能因为曾经完成就保持完成状态。

使用以下结构，先形成可审阅草稿：

```markdown
# <项目名> 写作任务清单
- 范围：全套 / 局部（明确章节）
- 当前版本及确认情况：

## 共同输入
<项目档案、招标、澄清、目录及spec的路径、版本/日期、大小、修改时间>

## 写作任务
### W-001 <标题>
- 范围及依据：<章节、当前决策编号、招标条款/页码>
- 所需材料：<路径及相关位置；缺口>
- 依赖：<真正必要的任务；无则无>
- 输出：<章节文件>
- 完成条件：<正文响应、证据或允许的待补登记>
- 状态：未开始 / 进行中 / 阻塞 / 已完成 / 需更新
- 下一步或阻塞原因：
```

## 3. 交接与更新

只对不清楚的粒度、依赖或范围集中询问一次；用户已明确要求按章拆分的，直接完成，不再索要形式上的确认。交付前检查：没有重复的主任务、依赖无循环、材料和输出都能定位到。

续接时从任务文件和来源版本恢复，只读取选中任务及其依赖，不要求重读全部历史对话。执行时用 `标书撰写`；全套或局部的范围标识要保留，局部任务全部完成不得触发全套检查。
